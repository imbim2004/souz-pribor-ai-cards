# Черновик карточки товара для B2B-магазина КИП

Прототип сервиса: на входе JSON о контрольно-измерительном приборе (название,
производитель, характеристики, описание), на выходе — черновик карточки товара,
который контент-менеджер правит, а не пишет с нуля:

- SEO-заголовок до 70 символов;
- SEO-описание на 800–1200 символов;
- структурированный список характеристик;
- 3–5 поисковых запросов под страницу;
- commercial-блок для менеджера: кому подходит, какие задачи решает, что уточнить.

LLM — Google Gemini (по умолчанию `gemini-3.5-flash`). Два входа: CLI и FastAPI
с простой веб-формой.

Главное требование задания — **модель не выдумывает технические значения**. Решено
тремя слоями: запрет в промпте, явная передача списка отсутствующих полей, и
машинная сверка чисел и единиц измерения вывода с входными данными после генерации
(см. [PROMPTS.md](PROMPTS.md)).

## Установка

```bash
git clone https://github.com/imbim2004/souz-pribor-ai-cards.git
cd souz-pribor-ai-cards
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

Python 3.11+ (проверено на 3.14).

## Переменные окружения

| Переменная | Обязательна | Назначение |
| --- | --- | --- |
| `GEMINI_API_KEY` | да | ключ Google Gemini API ([aistudio.google.com/apikey](https://aistudio.google.com/apikey)) |
| `GEMINI_MODEL` | нет | имя модели, по умолчанию `gemini-3.5-flash` |

Ключа в коде нет. Либо экспортом в оболочке, либо файлом `.env` рядом с проектом:

```bash
cp .env.example .env    # и впишите ключ
# или
export GEMINI_API_KEY=...
```

`.env` в `.gitignore` и в репозиторий не попадает.

Если API ответит `404` на имя модели, сервис сам запросит список доступных моделей
и напечатает их в сообщении об ошибке — останется поставить подходящую в
`GEMINI_MODEL`.

## Запуск: CLI

```bash
.venv/bin/python -m app.cli examples/product1.json
```

Варианты:

```bash
# результат в файл
.venv/bin/python -m app.cli examples/product2.json -o card.md

# JSON вместо Markdown (карточка + результаты проверок)
.venv/bin/python -m app.cli examples/product1.json --json

# вход со stdin
cat examples/product1.json | .venv/bin/python -m app.cli
```

Коды возврата: `0` — всё чисто; `1` — карточка собрана, но проверки нашли
расхождения или нарушение длин; `2` — ошибка во входных данных; `3` — ошибка
LLM API; `4` — не задан ключ.

## Запуск: веб-форма и API

```bash
.venv/bin/uvicorn app.web:api --reload --port 8000
```

- `GET /` — форма: вставить JSON, получить готовую карточку в Markdown;
- `POST /generate` — JSON-эндпоинт;
- `GET /health` — проверка живости и имя модели;
- `GET /docs` — схема OpenAPI.

### Пример запроса

```bash
curl -s -X POST http://127.0.0.1:8000/generate \
  -H 'Content-Type: application/json' \
  --data-binary @examples/product1.json
```

## Формат входных данных

```json
{
  "name": "Манометр показывающий ТМ-510Р.00 (0-2,5 МПа) G1/2",
  "manufacturer": "РОСМА",
  "specs": {
    "диапазон измерений": "0-2,5 МПа",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм"
  },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

Обязательно только `name`. Пустые значения, `"-"` и `"данных нет"` трактуются как
отсутствие данных: такие поля попадают в отчёт и в карточку со пометкой
«данных нет», а не домысливаются.

Значимыми для карточки КИП считаются поля из `EXPECTED_SPECS` в
[app/config.py](app/config.py): диапазон измерений, класс точности,
присоединение, диаметр корпуса, материал корпуса, рабочая температура, питание,
интерфейсы, степень защиты. Чего из них нет во входе — то перечисляется в
`checks.gaps`.

## Что проверяется после генерации

1. **Длины.** Заголовок ≤ 70 символов, описание 800–1200 символов, запросов 3–5.
   Не сошлось — сервис показывает модели замеры и просит переписать (до 2 повторов).
   Если и после повторов не сошлось, цифры честно выводятся в блоке «Проверки».
2. **Выдуманные значения.** Все числа и единицы измерения из вывода сверяются с
   входными данными; чего во входе не было — выводится списком.
3. **Подмена значений.** Если характеристика из входа исчезла из карточки или её
   число изменилось (например, МПа пересчитали в бар) — это тоже попадает в отчёт.

Проверки не блокируют выдачу: карточка отдаётся вместе с отчётом, решение за
человеком. В CLI ненулевой код возврата позволяет ловить такие случаи скриптом.

## Примеры

| Файл | Прибор | Заголовок | Описание |
| --- | --- | --- | --- |
| [examples/output1.md](examples/output1.md) | манометр РОСМА ТМ-510Р.00 | 55 символов | 974 символа |
| [examples/output2.md](examples/output2.md) | термометр биметаллический ПРОМА ТБ-100 | 61 символ | 1010 символов |

Входные данные — `examples/product1.json` и `examples/product2.json`, собраны из
YML-фида интернет-магазина (поля `name`, `vendor`, `typePrefix` и расшифровка
кода модели). Фид технических параметров не содержит — в нём из `param` есть
только «Артикул» и «Код товара», — поэтому часть значимых полей во входных данных
отсутствует намеренно: на этих примерах видно, как сервис сообщает о нехватке
данных вместо того, чтобы её закрыть выдумкой.

Оба файла `output*.md` — результат живого прогона CLI, руками не правились.

## Структура

```
app/
  config.py     настройки: модель, лимиты длин, повторы, значимые поля
  product.py    разбор входного JSON, фиксация пустых и отсутствующих полей
  prompt.py     системный промпт и промпт доводки длин
  gemini.py     REST-вызов Gemini: схема ответа, повторы, разбор ошибок
  checks.py     сверка чисел и единиц измерения с входом, проверка длин
  generator.py  оркестрация: генерация -> проверки -> повтор при нужде
  render.py     Markdown для контент-менеджера
  cli.py        вход 1: консоль
  web.py        вход 2: FastAPI (форма + /generate)
  web_form.py   HTML веб-формы
examples/       два прибора: входные JSON и реальный вывод модели
```

Промпты, принятые решения и ограничения — в [PROMPTS.md](PROMPTS.md).
