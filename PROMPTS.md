# Промпты, решения, ограничения

## 1. Какие промпты использованы

Полные тексты — в [app/prompt.py](app/prompt.py). Их три.

### 1.1. Системный промпт (`SYSTEM`)

Задаёт роль, запреты и формат. Ключевые блоки и зачем они нужны.

**Роль.** «Контент-редактор B2B-магазина КИП; результат — черновик, который будут
править, а не переписывать». Формулировка про черновик заметно снижает долю
маркетинговой воды: модель перестаёт «продавать» и начинает описывать.

**Запрет на выдумывание** — самая длинная часть промпта, потому что это главный
критерий задания. Общего «не выдумывай» мало: модель всё равно достраивает
правдоподобное. Поэтому перечислены конкретные классы значений, которые нельзя
придумывать: числа, единицы, диапазоны, классы точности, материалы, резьбы,
напряжения, интерфейсы, степени защиты, ГОСТ/ТУ, сроки поверки, гарантия, вес,
габариты.

Отдельным пунктом — **запрет пересчёта единиц**: «если на входе 0-2,5 МПа, в тексте
стоит 0-2,5 МПа, а не 25 бар». Без этого модель охотно переводит МПа в бар и
кгс/см², и формально она не врёт, а фактически в карточке появляется значение,
которого в паспорте прибора нет.

Тут же разрешено то, что запрещать не надо: **общие слова о назначении прибора**
(для чего нужен манометр, где применяется) — это не технические характеристики.
Без такого разрешения модель на скудном входе отказывается писать описание нужной
длины, потому что ей кажется, что любое утверждение надо подтвердить входными данными.

**Стиль.** Прямым списком запрещены клише («динамично развивающаяся компания»,
«широкий спектр решений»), восклицательные знаки, длинное тире, выдуманные цены,
сроки поставки и наличие на складе. Негативные инструкции работают здесь лучше
положительных: «пиши по-деловому» модель понимает как «пиши красиво».

**Формат.** JSON по описанной схеме с пояснением к каждому полю: что считать в
символах, что переносить из входа без изменений, какими должны быть запросы.
Схема дублируется на уровне API (`responseSchema` в [app/gemini.py](app/gemini.py)),
поэтому парсить markdown-обёртки не приходится.

### 1.2. Сообщение с данными (`build_user_message`)

Входные данные отдаются как JSON — ровно те поля, что пришли, без пересборки в
прозу. Модель лучше держит соответствие «характеристика → значение», когда видит
структуру, а не абзац.

Ниже — **явный список отсутствующих полей** с инструкцией вернуть их в
`missing_data` и в `specs` со значением «данных нет». Это главная находка: пока
список не передавался, модель либо молчала о пробелах, либо закрывала их
догадками. Когда пробелы названы заранее, она честно пишет «данных нет» и
переносит их в блок «что уточнить» для менеджера.

### 1.3. Промпт доводки длин (`build_length_fix`)

Если ответ не прошёл проверку длин, модели отправляется третья реплика: список
замеров («seo_description содержит 712 символов, нужно не менее 800») и требование
переписать JSON целиком, сохранив значения характеристик и меняя только текст о
назначении и применении. Оговорка про «не добавляй новых технических значений»
нужна, потому что первый порыв модели при добивке длины — досыпать характеристик.

Проверено живьём: при искусственно поднятой планке (1150 символов вместо 800)
первый ответ дал меньше нормы, второй — 1152 символа, список выдуманных значений
остался пустым.

## 2. Принятые решения

**Gemini + REST вместо SDK.** Прототипу нужны три вещи: JSON-схема ответа,
таймаут и повторы. Всё это есть в обычном `requests`-вызове, зато нет зависимости,
которая ломается со сменой мажорной версии SDK. Модель по умолчанию —
`gemini-3.5-flash`: заметно дешевле и быстрее pro, а задача не творческая.

**JSON от модели, Markdown на выходе.** Модель возвращает структуру, а Markdown
собирает код ([app/render.py](app/render.py)). Если бы Markdown писала модель,
проверять длины и сверять характеристики пришлось бы по тексту, а таблицу
характеристик нельзя было бы отдать в CMS отдельным полем.

**Три слоя против выдумок, а не один.** Промпт запрещает, сообщение с данными
называет пробелы, а [app/checks.py](app/checks.py) после генерации сверяет
результат с входом. Проверка намеренно простая и объяснимая: числа нормализуются
(`2,50` и `2.5` — одно и то же), единицы ищутся по границам слова рядом с числом,
и всё, чего нет во входных данных, выводится списком. Никаких оценок уверенности
и прочих «умных» слоёв: контент-менеджеру нужен список расхождений, а не вероятность.

**Обратная сверка.** Кроме «появилось лишнее» проверяется «пропало своё»:
характеристика из входа, не попавшая в карточку, и изменённое число в значении.
Именно так ловится пересчёт МПа в бар — формально новых чисел нет, но значение
подменено.

**Проверки не блокируют выдачу.** Карточка отдаётся вместе с отчётом: решение за
человеком, прототип не должен молча съедать результат. Для скриптов в CLI есть
ненулевой код возврата.

**Поле «что уточнить» исключено из сверки чисел.** Оно по смыслу перечисляет то,
чего во входе нет («уточнить степень защиты IP»), и буквальная проверка на нём
срабатывала всегда. Остальные поля — заголовок, описание, характеристики, запросы,
«кому подходит», «какие задачи» — сверяются.

**Ошибки разведены по типам.** `400` — виноват вход, `502` — внешний сервис,
`500` — не настроен ключ; в CLI тем же смыслам соответствуют коды `2`, `3`, `4`.
Повторяются только сетевые сбои, `429` и `5xx`; `400`, `401/403` повторять
бессмысленно, и код этого не делает. На `404` по имени модели сервис сам
запрашивает список доступных моделей и печатает его в сообщении об ошибке.

## 3. Откуда взяты примеры

Входные JSON собраны из YML-фида интернет-магазина (47 964 товара). Важная
деталь: **технических характеристик в фиде нет** — из тегов `param` в нём
встречаются только «Артикул» и «Код товара», а описаний нет вовсе. Поэтому
`specs` собраны из названия модели, `typePrefix`, `vendor` и расшифровки кода
модели по схеме производителя:

- `ТМ-510Р.00(0-2,5 МПа)G1/2` → серия, диапазон, присоединение, исполнение
  штуцера; диаметр корпуса 100 мм закодирован в номере серии;
- `ТБ-100-О-211-120-G1/2-100-1,5` → диаметр корпуса 100 мм, осевое исполнение,
  модель 211, верхний предел 120 °C, присоединение G1/2, длина погружной части
  100 мм, класс точности 1,5.

Поля, которых расшифровка не даёт (материал корпуса, степень защиты, рабочая
температура среды), оставлены пустыми намеренно — ровно для того, чтобы на примерах
было видно поведение при неполных данных. В первом примере пустых полей больше,
во втором меньше.

Тексты `description` во входных JSON описывают назначение прибора и не содержат
чисел, которых нет в `specs`.

## 4. Ограничения решения

1. **Карточка — черновик, а не публикация.** Общие формулировки о применении
   модель пишет сама; фактическую проверку «действительно ли этот прибор ставят на
   пар» никто не делает. Это осознанный компромисс: иначе на скудном входе
   описание в 800 символов не собрать.
2. **Сверка чисел буквальная.** Она ловит появление новых чисел и единиц, но не
   понимает смысла. Число, случайно совпавшее с чем-то из входных данных,
   проверку пройдёт; безобидное число в общей фразе — наоборот, попадёт в список
   расхождений. Список расхождений — подсказка человеку, а не приговор.
3. **Единицы измерения — фиксированный список** в `checks.py`. Экзотическая
   единица, которой в списке нет, не будет замечена. Список расширяется по месту.
4. **Нет собственной расшифровки кода модели.** Сервис не знает, что «510» в
   `ТМ-510Р` означает корпус 100 мм. Такие знания надо класть во входные данные
   (это и сделано в примерах) либо подключать справочник серий.
5. **Длины гарантируются не всегда.** Модель держит 800–1200 символов, но при
   совсем бедном входе может не дотянуть. Тогда делается до двух повторов, а
   остаток выводится числом в блоке «Проверки» — незаметно обрезать или добить
   текст сервис не станет.
6. **Внешний сервис бывает перегружен.** Gemini отвечает `503 high demand`
   неравномерно: `gemini-3.8-flash` в день разработки отдавал 503 почти всегда,
   `gemini-3.5-flash` — изредка. Повторы с паузами 2/4/8 секунд это покрывают,
   но прогон может занять до минуты.
7. **Нет кеша, очереди и батча.** Каждый запрос — отдельный вызов модели. Для
   пачки в несколько тысяч товаров нужна очередь и ограничение параллельности.
8. **Нет тестов.** Для прототипа проверка живыми прогонами обоих примеров и
   ручной перебор ошибочных входов; на продолжении — pytest на `product.py`,
   `checks.py` и `render.py` с замоканным API.
9. **Нет авторизации у веб-формы.** Поднимать её наружу в таком виде нельзя:
   открытый эндпоинт тратит квоту ключа.

## 5. Что улучшить дальше

- **Справочник серий и типов приборов.** Таблица «серия → диаметр корпуса, класс
  точности, материалы» убирает большую часть «данных нет» и повышает качество
  карточек без участия модели.
- **Загрузка фида целиком.** Сейчас вход — один товар; для магазина нужен приём
  YML/CSV, дедупликация по группам (в фиде одна модель представлена десятками
  исполнений) и генерация одной карточки на группу с таблицей исполнений.
- **Единая карточка на группу модификаций.** Сорок манометров одной серии
  отличаются диапазоном и резьбой; им нужна одна страница с таблицей, а не сорок
  почти одинаковых текстов — иначе страницы конкурируют между собой в поиске.
- **Проверка на уникальность текста** между карточками одной серии: сравнение
  шинглами перед публикацией.
- **Подбор поисковых запросов по данным,** а не из головы модели: Wordstat или
  внутренний поиск магазина. Сейчас запросы правдоподобны, но частотностью не
  подтверждены.
- **Человек в цикле.** Экран «принять / править / отклонить» с сохранением правок
  даёт материал для дообучения промпта: правки контент-менеджера — это и есть
  разметка.
- **Кеш по хешу входных данных,** чтобы повторный прогон того же товара не стоил
  вызова модели.
